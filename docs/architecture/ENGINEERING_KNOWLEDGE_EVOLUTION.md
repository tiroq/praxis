# Engineering Knowledge Evolution

Status: ACTIVE

---

# Purpose

Engineering knowledge must evolve.

Praxis should become easier to engineer after every implementation.

Every completed task is an opportunity to improve the engineering system itself.

---

# Principle

Never solve the same engineering problem twice.

The second solution should improve engineering knowledge.

The third solution should improve engineering automation.

---

# Evolution Rules

A solution starts as code.

If reused:

becomes Reference.

If repeated:

becomes Pattern.

If mandatory:

becomes Policy.

If verifiable:

becomes Checklist.

If sequential:

becomes Playbook.

If AI performs it:

becomes Prompt.

If multiple prompts cooperate:

becomes Workflow.

If every implementation uses it:

becomes Platform Capability.

---

# Promotion Criteria

## Code → Reference

Requirements

Production quality.

Architecturally reviewed.

RFC compliant.

Simplest known implementation.

No hidden coupling.

---

## Reference → Pattern

Requirements

Observed repeatedly.

Multiple implementations.

Reusable architecture.

Clear responsibilities.

---

## Pattern → Policy

Requirements

Required everywhere.

Violations are harmful.

Review can verify compliance.

---

## Policy → Checklist

Requirements

Binary verification possible.

PASS / FAIL.

No interpretation required.

---

## Checklist → Playbook

Requirements

Multiple checklists executed together.

Order matters.

Dependencies exist.

---

## Playbook → Prompt

Requirements

AI can execute.

Inputs defined.

Outputs defined.

Quality gates defined.

---

## Prompt → Workflow

Requirements

Multiple prompts cooperate.

Responsibilities separated.

Feedback exists.

---

## Workflow → Automation

Requirements

Zero human coordination.

Deterministic.

Recoverable.

Observable.

---

## Automation → Platform Capability

Requirements

Invisible.

Always used.

Trusted.

No longer optional.

Did we discover a better implementation?

Did we improve architecture?

Did we simplify a pattern?

Did we create a reusable example?

Did we discover a recurring checklist?

Did we improve a workflow?

Did we improve a prompt?

# Anti-patterns

Never promote after one implementation.

Never create documents without evidence.

Never automate unstable processes.

Never invent patterns.

Never invent abstractions.

Never document hypothetical knowledge.

---

# Engineering Debt

Knowledge debt exists when

same review repeated

same bug repeated

same comments repeated

same architecture discussion repeated

same prompt rewritten

same checklist rediscovered

same implementation style reinvented

Knowledge debt should be paid before technical debt whenever possible.
